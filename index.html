01 · Why

      
Built for research with AI agents

      
Social science research is no longer done only by people. More and more of the work is shared with an army of AI agents, and that brings new challenges. We built this template to meet them: a clear folder structure for every project, with AI built into the workflow from the first commit. Here are four reasons to try it.

      

        
          🗂️
          01
          
Universal template

          
Same structure and one entry point for all your projects, so anyone, human or agent, can find anything.

03 · AI agents

      
Agents follow the same rules as your RAs

      
The template ships AGENTS.md: standing instructions that most coding agents load when a session starts. The AISS Lab keeps refining these rules based on what works in real projects; the current version is below. Open a group to read it.

      
Data 4 rules
    
        
  • data/raw/ and data/llm_cache/ are read-only: never edited, overwritten, moved or deleted.
    • 
        
  • Data moves one way: build scripts write to interim/ and clean/; analysis reads only clean/ and writes only to output/.
    • 
        
  • A new source gets an entry in data/README.md before any code uses it.
    • 
        
  • Variables in data/clean/ are defined in data/codebook.md: read it before creating or interpreting a variable, and update it in the same commit.

      
Paths and environment 4 rules
    
        
  • No hard-coded paths: Python uses lib.paths, Stata uses the globals from 00_setup.do.
    • 
        
  • Python packages only through uv add; never pip install, never edit uv.lock.
    • 
        
  • Stata packages install into code/ado/, and only after asking.
    • 
        
  • Keys come from environment variables, never from code, notebooks or logs.

      
The pipeline 3 rules
    
        
  • Every new script goes into STEPS in run.py, in run order.
    • 
        
  • Tables and figures are written by code; no number is typed into the paper by hand.
    • 
        
  • Experiments go in scratch/, and nothing may depend on it.

      
LLM calls 2 rules
    
        
  • Every prompt and raw response is saved to data/llm_cache/ before processing; the cache is checked before calling again. A retired model cannot be asked twice.
    • 
        
  • Each call records the exact model and version, the date, temperature and seed.

      
Git, and when to stop 3 rules
    
        
  • Work on a branch named type/task, where type is data, analysis, paper or fix (for example data/merge-counties); never on main. Small commits that say what changed and why.
    • 
        
  • Run the affected steps before calling a task done.
    • 
        
  • Ask before any choice that changes results: sample, variable definitions, specifications, dropped observations, missing data. State the options; don't choose silently.

      
Project specifics written by you
        
The last section of AGENTS.md is yours. It gives every agent, and every new RA, the context only you have. For example:

        
    
        
  • The research question, in one sentence.
    • 
        
  • The main datasets: what they are and where they come from.
    • 
        
  • Decisions already made, such as the sample period, the unit of observation or the main specification.
    • 
        
  • Naming conventions for variables and files.
    • 
        
  • Anything else a new RA would need to know before touching the code.

    

    

      
04 · Environment and secrets

      
Same packages everywhere, secrets nowhere

      
Python packages are managed by uv. You never edit the package files by hand: uv does it, and Git records the result. Stata packages install into code/ado/, so they travel with the project. To set it all up on your computer, follow the step-by-step setup.

      

        

          
CommandWhenWhat happens

          
            
uv syncAfter cloning, and after every git pullReads uv.lock and builds .venv/ with exactly those versions.

            
uv add pandasYou need a new packageAdds it to pyproject.toml, pins the exact version in uv.lock, installs it. Commit both files.

            
uv run python run.pyEvery time you run codeRuns inside the project environment, no activation needed.

            
uv remove pandasA package is no longer usedRemoves it from both files and from .venv/.

          
        

      

      

        

          
.env.example Tracked


DATA_DIR=data
STATA_PATH=
OPENAI_API_KEY=
ANTHROPIC_API_KEY=

          
The names of what the project needs, without values. Everyone sees it on GitHub.

        

        

          
.env Ignored


DATA_DIR=/Volumes/aiss-lab/census
STATA_PATH=/Applications/Stata/…/stata-mp
OPENAI_API_KEY=sk-proj-••••••••••••
ANTHROPIC_API_KEY=sk-ant-••••••••••••

          
Your own values. Never committed, never pasted into code, a notebook or a chat.

        

      

      
Committed a key by mistake? Deleting the file is not enough: the key stays in Git's history. Revoke it with the provider right away, then create a new one.

    




    

      
05 · Collaboration

      
You and your RAs, on the same page

      
The template gives you and your RAs one shared routine.

      

        
While working
A branch per task
RAs never work on main. Each task gets its own branch, named type/task (for example data/merge-counties), so work in progress never breaks the project.

        
Every session
A log entry
Five minutes at the end in docs/log/<name>.md: what was done, found and decided, and why.

        
Before each meeting
A weekly update
One page in docs/updates/: results, problems and the decisions you need to make.

        
After each meeting
GitHub issues
Each to-do from the meeting becomes an issue assigned to an RA. Open issues are the RA's task list.

      

      

        
        
      

      

        

## 2026-10-20 · [name]

**Did:** what you worked on, with the scripts or commits involved.
**Found:** results, surprises, anything that did not behave as expected.
**Decided:** choices you made and why (or that wait for the PI).
**Next:** where to pick up next session.
**Questions for PI:** anything that needs their call.

      

      

        

# Update · week of 2026-10-20

## Done
- [what moved forward, with links to tables or figures in output/]

## Results worth discussing
- [the one or two things the meeting should look at]

## Problems
- [what is blocked and what would unblock it]

## Decisions needed from the PI
- [each with the options and your suggestion]

## Plan for next week
- [three items at most]

      

    

    

      
06 · Step-by-step setup

      
From zero to a running project

      
Tick each step as you go.

      
    
        
  1. 
          
          
    
            
      
              
    • Click Use this template (the same button is at the top of this page and on the repository page).
      • 
              
    • Choose the owner: your own account, or aiss-unibocconi-eu for lab projects.
      • 
              
    • Give the repository a name. Short, lowercase names with hyphens work best, for example census-migration. You will use this name in the next step.
      • 
              
    • Make it Private.
      • 
            
    
            
    What this didYou now have your own copy of the template on GitHub, with every folder and rule on this page, ready for your project. Because it is private, only the people you invite can see it.
    
        
    2. 
        
  2. 
          
          
    
            
      
              
    • Open a terminal: Terminal on Mac, PowerShell or Git Bash on Windows.
      • 
              
    • In the terminal, check that Git is installed: run git --version. If you get an error, install Git first.
      • 
              
    • In the terminal, go to the folder where you keep your projects, for example cd ~/Projects.
      • 
              
    • Run the command below, with my-project replaced by the name you chose in step 1 (and your own account in place of aiss-unibocconi-eu if the repository is yours). Then cd my-project to step into the new folder.
      • 
            
    
            
    git clone https://github.com/aiss-unibocconi-eu/my-project.git
    
            
    What this didThe project now lives on your computer too, linked to GitHub. From here Git records every change you make: you can commit, push to GitHub, and undo, and your RAs work on exactly the same code.
    
        
    3. 
        
  3. 
          
          
    
            
      
              
    • In the terminal, inside your project folder, copy the example file .env.example to a new file named .env. .env exists only on your computer.
      • 
            
    
            
    cp .env.example .env
    
            
      
              
    • Open it in any text editor.
      • 
              
    • Fill in one value per line, after the = and with no spaces around it:
                
        
                  
      • DATA_DIR: the folder where the project's data lives, for example the lab storage folder. Keep data to store it inside the project.
        • 
                  
      • STATA_PATH: the full path to your Stata program, only if the project has .do files. On Mac, for example /Applications/Stata/StataMP.app/Contents/MacOS/stata-mp; on Windows, C:\Program Files\Stata18\StataMP-64.exe.
        • 
                  
      • OPENAI_API_KEY, ANTHROPIC_API_KEY: your own API keys, only if the project calls language models. Otherwise leave them empty.
        • 
                
      • 
              
    • Save the file. Never commit it, and never paste your keys into code, notebooks or chats.
      • 
            
    
            
    What this did.env holds what differs from machine to machine: your data folder, your Stata path and your keys. Git ignores it, so your secrets never reach GitHub while everyone shares the same code.
    
        
    4. 
        
  4. 
          
          
    
            
      
              
    • In the terminal, check that uv is installed: run uv --version. If you get an error, install uv first.
      • 
              
    • Still inside the project folder, run the two commands below. The first installs Python and the packages, the second runs the project.
      • 
              
    • The first step of run.py checks your setup. It ends with setup looks good, or tells you exactly what is missing.
      • 
            
    
            
    uv sync
uv run python run.py
    
            
    What this diduv installed the exact package versions recorded in uv.lock, so your numbers will match everyone else's. run.py checked your setup, and from now on this one command rebuilds the whole project.
    
        
    5. 
        
  5. 
          
          
    
            
      
              
    • Replace [Project title] with your project's name.
      • 
              
    • Under Question, write in two sentences what the project wants to learn and why it matters.
      • 
              
    • Fill in the Team table: you as PI, and your RAs.
      • 
              
    • Delete the "Starting from the AISS template?" box at the top.
      • 
            
    
            
    What this didAnyone who opens the repository, a co-author, a new RA or an AI agent, now sees what the project is about and how to run it, without having to ask you.
    
        
    6. 
        
  6. 
          
          
    
            
      
              
    • In AGENTS.md, scroll to Project specifics at the end. Write the research question in one sentence, the main datasets, your naming conventions, and anything else a new RA would need to know.
      • 
              
    • In .gitignore, add anything else that must not go to GitHub, one entry per line at the end, for example a folder of large files (exports/) or files from another program (*.dta). The lab defaults for data, .env, logs and scratch are already there.
      • 
            
    
            
    What this didEvery AI agent session now starts with the same context as your RAs, so you don't explain the project again each time, and Git knows everything that must stay off GitHub.
    
        
    7. 
        
  7. 
          
          
    
            
      
              
    • Replace the example with a section for each clean dataset you plan, and one line on what a row is (for example, county × census year).
      • 
              
    • List the main variables you already know you will use: name, label, type and unit, and how each is defined. Your RAs and their agents add the rest as they build them.
      • 
            
    
            
    What this didEveryone, human or agent, now uses the same definitions for your key variables instead of guessing them from the code.
    
        
    8. 
        
  8. 
          
          
    
            
      
              
    • Save all the files you edited.
      • 
              
    • In the terminal, inside your project folder, run the three commands below. The first two record your changes, the third uploads them to GitHub.
      • 
            
    
            
    git add -A
git commit -m "Describe the project"
git push
    
            
    What this didYour first commit is on GitHub and the project is set up. Your RAs can now clone it and start from exactly where you are.
    
        
    9. 
      

      
0 of 8 done
